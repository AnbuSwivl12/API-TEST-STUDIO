Three ways out of the three-column screen

The runner works: 102 canned cases against the Swivl Template API, a token, a Run All, a CSV at the end. What it doesn't do is tell you how the run went. Below are three structurally different answers — not three skins — each shown at desktop width with a full 102-case load, a real mixed-status run, and one failure opened.

Mockups only — index.html untouched Dark theme, the product default Constraint: one file, vanilla JS, no build Data: the real PRESET_CASES

What each direction has to answer for

P1 — duplication

Two panes show the same request

The doc pane restates the method, URL, expected result and cURL that the Try It pane is already holding. Three columns, roughly two columns of information.

P2 — no results view

102 cases run, five tiles reported

After Run All you know 12 failed. Which twelve, and why, is a hunt down the sidebar clicking red dots one at a time.

P3 — setup reads as config

Six bare inputs in the topbar

Env, base URL, API version, auth type, token, gear. Nothing says "you are hitting Stage as this user, and the token is still good."

P4 — no progress, no history

A 3px bar and then it's gone

No live count while 102 requests go out, no record of the previous run, no way to see that TC_020 has failed the last three times.

Direction A

The run is the document

The centre of the app stops being "the case you clicked" and becomes the run you just finished. Failures sort to the top, grouped by shared cause, and open in place — expected vs actual side by side — so the third column disappears entirely. The sidebar demotes to a tag rail with per-tag pass bars, because once you have a report you navigate by what broke, not by alphabet.

Optimizes for

  • Triage after Run All. Twelve failures, four causes, zero clicks to see the first one.
  • Reporting. The screen already is the CSV — screenshot it into a ticket.
  • Regression reading. Run #47 vs #46 delta sits next to the title.

Trades away

  • Exploratory poking. Editing a URL and re-sending moves into a drawer off the row.
  • Browsing by endpoint. The 102-row list is gone; you reach a case by tag, search, or failure.
  • Cold start. Before the first run the report is empty and has to sell "press Run All".

Retrofit cost — single file, no build

moderate · mostly deletion

Needs a state.runs array (cap it at ~10 and truncate bodies — localStorage is 5 MB and 102 JSON responses will blow it), plus a cause-grouping pass over results. renderDoc() and renderTry() collapse into one renderer, so this removes more code than it adds. No new dependencies.

Direction B

One session chip, one column, one palette

Keep the runner's shape but strip the chrome. The six topbar inputs collapse into a single session chip that reads like a sentence — Stage, as this token, for 41 more minutes — and opens as a popover when you actually need to change something. Everything else that lived in the topbar moves into ⌘K. The doc and Try It panes merge into one request-then-response column, and Run All lands in a bottom dock that streams progress and collects failures as they happen.

Optimizes for

  • The daily driver. Fastest path from "paste token" to "send" of the three.
  • Trust in the setup. Token validity and env are stated, not implied by an input's contents.
  • Keeping the current mental model. Still a list plus a request pane.

Trades away

  • Discoverability. Actions hidden behind ⌘K are invisible to a first-time QA; the dock and chip carry the whole affordance load.
  • Depth on results. The dock ranks failures but never becomes a real report — worst of the three for a 12-failure post-mortem.
  • Screen real estate for history. Nowhere for run #46 to live.

Retrofit cost — single file, no build

light · cheapest of the three

The chip and popover reuse the existing .modal-backdrop pattern; the dock is the #progressBar grown up. Real work is the palette — substring match, arrow-key nav, focus trap, Escape — call it ~200 lines of plain JS, no library. Merging the panes deletes the duplicated blocks in renderDoc().

Direction C

A test suite, not a request builder

Stop pretending this is Postman. 102 cases with statuses, durations and a history is a table, and QA already knows how to work one: sort it, facet it, multi-select it, export it. Each row carries a ten-run trend, which is the only honest way to tell a real regression from a flake. Detail opens in a sheet docked beside the table so you never lose your place in the list, and Runs becomes a real top-level section.

Optimizes for

  • Scale. The only direction where 102 rows — or 400 — stays comfortable.
  • Evidence. Trend column plus a flaky facet answers "is this new?" without opening anything.
  • Bulk work. Select 9, mark blocked, re-run the rest — the existing bulk bar finally has a surface.

Trades away

  • The console feel. Reads like a spreadsheet; the pleasant "docs on the left, playground on the right" quality is gone.
  • Room for the response. A 420px sheet is a tighter reader than today's full centre pane.
  • Simplicity. Adds a second top-level mode and a stored history — the most machinery.

Retrofit cost — single file, no build

heavy · needs a data migration

102 rows render fine unvirtualised, but per-case history is new persisted state: keep it to {code, ms, at} × 10 (~1,020 tiny records) and version the localStorage key so existing saves migrate instead of resetting. Sorting, faceting, the sheet and the Runs view are genuinely new code — roughly double A. Still zero dependencies.

All three mockups are the product's dark theme, driven by the same custom properties index.html already defines — nothing here needs a new token. Direction C is the one that also wants a good light theme: a dense table is what people read for an hour straight, and the existing [data-theme="light"] block covers it without change.

Common ground worth taking whichever direction wins: the session chip from B, run history from A or C, and grouping failures by shared cause — four 405-expected cases returning 404 is one bug, and every view here should say so.
