API Test Studio · round two · builds on the shipped Run Report

One module at a time

Round one asked how to read a run; Direction A shipped and the Run Report is in the product. This round answers the next three asks — make it minimal, make Swagger module-wise, make it fast. They turn out to be one problem: the app currently believes there is exactly one API in the world, so every knob for that one API has to live in the topbar at once, and every run has to be the whole 102.

Mockups only — index.html and design-directions.html untouched Dark theme, the product default Constraint: one file, vanilla JS, no build Data: PRESET_CASES + the six real test workbooks

§0 — what I found before drawing anything

Two numbers in the brief are off, and both make the case stronger

Chaining

Not 7 blocked cases — 33

Counted straight out of PRESET_CASES: 33 of 102 paths contain {id}, 8 also contain {sectionId}, 2 contain {subId}, 1 contains {fieldId}. A third of the suite is unrunnable without a value carried from a previous response, not 7 %.

Concurrency

The throttle isn't the bottleneck

102 × 120 ms of throttle is 12 s. The run takes minutes because two cases — TC_028 oversized query and TC_037 simulated downstream failure — sit on the 30 s default timeout. A pool alone gets you to 31 s and no further; the timeout is the critical path.

Scope

Seven modules, 411 cases

Templates 102 + Job Detail 94 + Recurring SLA 101 + Billing 30 + Building Unit 30 + Job Detail Exclusions 30 + Customer Availability 24. Loading all of them into one flat list is the thing the module concept exists to prevent.

§2 — module-wise Swagger

A module is a spec, a host, a case list and a run history — bundled

Today state.swaggerSpec is a single slot and state.cases is a single flat array, so attaching the Billing spec means throwing away the Templates one. The fix is not a second slot; it is admitting the app has always been holding one module and giving that thing a name, an identity and a plural.

Owned by the module

Switches when you switch

OpenAPI spec · service host key · x-api-version · case list · tag taxonomy · smoke set · fixtures & captured chain variables · run history · colour swatch.

Why version is here: Building Unit's entire suite is 6.1.0-vs-6.2.0 behaviour and two Customer Availability routes need ≥ 5.7.0. A single global version box makes those suites impossible to hold at the same time.

Owned by the session

Survives every switch

Environment (Stage / Local / Custom) · auth type · bearer token · CORS proxy · timeout · theme · cloud-sync credentials.

Why auth is here: it is the same tenant token for every Swivl service. Making it per-module would mean pasting the same JWT seven times and re-pasting all seven when it expires in 41 minutes.

Base URL stops being a field and becomes a lookup

The module names a service; the session names an environment; the base URL is the cell where they meet. That is the whole reason the Base URL input can leave the topbar — and it is also why switching module while staying on Stage does the right thing without touching anything.

Retrofit: ~180 lines. Every existing read of state.cases / state.swaggerSpec / state.runs goes through three one-line accessors (mod(), cases(), runs()) — a mechanical find-and-replace across roughly 60 call sites. Migration for existing users: wrap whatever is in localStorage into a module called "Templates" and set it active, so a returning user sees exactly their current state with a chip on top. client-side only
Storage is the one real constraint. localStorage is ~5 MB and save() already sheds old runs when it overflows. Seven modules × run history will hit that wall. Fix without a server: keep the case lists in localStorage (small — 411 cases is ~180 KB) and move runs to IndexedDB, which is same-origin, needs no build step, and has a quota in the hundreds of MB. ~50 lines with a tiny promise wrapper. still client-side

Running across modules, and what the Report does about it

Yes, you can run across modules — but not by merging the lists. A suite is a saved set of modules with a scope each; running it executes them back-to-back, module by module, and writes one run record per module plus a thin suite header that links them. That keeps every existing Run Report behaviour intact, because each report still describes one module against one base URL.

§3 — efficient

Concurrency buys 3×. The timeout buys the other 3×.

Measured against the real suite at 240 ms average latency: 102 sequential requests plus 120 ms of throttle each is 96 s, and two thirds of that is TC_028 and TC_037 sitting on the 30 s default. A pool of six drops it to 31 s — and then stops dead, because one 30 s request is now the whole critical path. Both fixes together get the suite under 12 s.

Mid-run — six lanes, 8.4 s in

// replaces the for-loop in runAll() — ~40 lines, no library
async function runPool(targets, limit = 6) {
  const serial = targets.filter(c => c.serial);       // TC_034 / 035 / 036
  const pooled = targets.filter(c => !c.serial);
  let i = 0;
  const worker = async () => {
    while (i < pooled.length && !runCtl.stopped) {
      const c = pooled[i++];
      await waitForDeps(c);                        // §3.2 — resolves {{vars}}
      await sendRequest(c);                        // unchanged
      onResult(c);                                   // stream into tray + rail + feed
    }
  };
  await Promise.all([...Array(limit)].map(worker));  // N workers, one queue
  for (const c of serial) { await sendRequest(c); onResult(c); }
}
Retrofit ~40 lines plus ~70 for the tray markup and its per-result render. sendRequest(), buildUrl(), buildHeaders() and snapshotResult() are untouched — they are already per-case and stateless. client-side only — Promise.all over a fixed worker count is real parallelism in one tab Two browser limits to respect: Chrome allows 6 concurrent connections per origin over HTTP/1.1, which is why the default is 6 and 10 is offered rather than 20. Over HTTP/2 to a single host the ceiling is far higher, so the slider is worth having.
Per-case timeout needs a decision, not code. Dropping the global 30 s to 10 s is one number, but TC_037 expects 500/503 from a downstream failure and may legitimately be slow. The proposal is a timeoutMs field per case, defaulting to the module's value, set to 10 s on the two known offenders — visible in the case editor so it is never a mystery why one case gave up early.

Two sources of values, because the modules genuinely differ. Fixtures are typed once and stored on the module — right for Job Detail, whose workbook already names the job (JSSS01186). Retrofit ~70 lines. Three pieces: a five-line {{var}} interpolator run over path / query / headers / body just before buildUrl(); a ~25-line getter supporting the $.a.b[0].c subset of JSONPath (a dotted-path walker with bracket indices — not a JSONPath library); and a pre-pass that reads every case's {{vars}} and capture to build the dependency edges the pool waits on. Cycles are rejected at run start with a named pair, not discovered at runtime. client-side only
Ordering caveat worth stating. TC_071 deletes the draft and TC_072 deletes a published one — chaining them off the same captured templateId means the second gets a 404 from an already-deleted resource. Destructive cases need their own producer, so TC_054 should be marked reusable:false and re-run per consumer, or the module should carry a fixture template that is never deleted. This is a test-design decision the app can surface — flag it when two consumers of one capture both use DELETE — but it cannot resolve it.

Left alone, on purpose

Not touching

The request builder

The three-column Params / Headers / Body editor and the response pane work. Round one proposed restructuring them; this round adds a chip and a Capture tab and otherwise leaves them exactly as they are.

Not touching

The four upload cases

TC_095–TC_098 stay blocked. Multipart with a real file is possible in a browser, but the cases need fixture files of specific sizes and MIME types that no one is going to re-pick every session. They keep their honest "use curl" note.

Not touching

Assertions beyond status code

Most workbook rows have an ExpectedResult in prose — "fullAddress = addressLine1 + ', ' + city…". Turning those into runnable body assertions is the highest-value thing left, and it is a whole round of its own.

Still needs a server

CORS

Unchanged. Cross-origin requests still need the API to send the headers or a proxy in Settings. Modules make this slightly worse — two hosts to get CORS right on instead of one.

Still needs a server

Scheduled / CI runs

A tab that isn't open runs nothing. Nightly regression across all seven modules is a CI job, and the right shape for it is exporting the modules as JSON and running them in a Node harness — not pretending the browser can do it.

Still needs a server

Sharing modules with the team

The cloud-sync worker already in the repo could carry modules instead of one blob, which would make "here is the Billing module" a link. Out of scope here, but the data model above is shaped so it would be a small change.
